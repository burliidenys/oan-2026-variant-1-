Оптимізація бази даних: Індексація
У проєкті реалізовано створення індексів для покращення продуктивності системи при роботі з великою кількістю заявок.
В рамках міграції бази даних (schema.sql або папка migrations) додано наступні структури:

idx_requests_created_at: Індекс для поля createdAt у таблиці requests.

idx_requests_status_id: Індекс для поля statusId.

Технічне обґрунтування:
Прискорення сортування (ORDER BY);
Швидка фільтрація (WHERE);
Як перевірити наявність індексів
EXPLAIN QUERY PLAN SELECT * FROM requests WHERE statusId = 1 ORDER BY createdAt DESC;




Перелік таблиць: 
Архітектура даних
База даних складається з чотирьох взаємопов’язаних таблиць, що забезпечує нормалізацію та швидкість обробки запитів:
users: Зберігає унікальні імена користувачів  -- Реєстр користувачів системи.  -- id (Primary Key)
statuses: Довідник станів заявки (Pending, Approved, Rejected). -- id (PK), name (Unique)
access_types: Довідник типів доступу (Temporary, Admin, тощо). -- id (PK), name (Unique)
requests: Головна таблиця із заявками на доступ. -- id (PK), userId (Foreign Key), statusId (FK)

Проєкт використовує зв'язки типу один-до-багатьох (1:N):
users → requests (1:N): Один користувач може створювати безліч заявок, але кожна заявка належить лише одному конкретному користувачу.
statuses → requests (1:N): Кожен статус (наприклад, "Pending") може бути призначений багатьом заявкам.
access_types → requests (1:N): Один тип доступу може використовуватися у великій кількості різних заявок.


Система автоматичних міграцій та Seed-даних
Для забезпечення стабільності розгортання в проєкті реалізовано кастомний Migrator. При запуску сервера він виконує наступні кроки:
Перевірка стану: Створюється службова таблиця schema_migrations, яка відстежує вже застосовані SQL-файли. Це запобігає повторному вставленню даних при перезапуску сервера.
Ініціалізація структури: Через файл 001_init.sql база даних створює всі необхідні таблиці лише у разі їх відсутності.
Генерація початкових заявок: Файл 002_seed.sql автоматично наповнює базу п’ятьма початковими користувачами та відповідними заявками. Це гарантує, що журнал заявок не буде порожнім при першому запуску додатка або після видалення файлу database.db.

Для забезпечення валідності даних на рівні ядра бази даних впроваджено такі обмеження:

NOT NULL: Застосовано до всіх критичних полів (details, userId, statusId, name). Це гарантує, що база не прийме порожню заявку або користувача без імені.
UNIQUE:
У таблиці users для поля name (не може бути двох користувачів з однаковим логіном).
У таблицях-довідниках для назв статусів та типів доступу.
FOREIGN KEY: Використовується в таблиці requests для полів userId, statusId та accessTypeId. Це запобігає появі "сирітських" записів (неможливо створити заявку для неіснуючого користувача).
DEFAULT: Для поля statusId встановлено значення за замовчуванням, що відповідає статусу "Pending" (ID: 1).
CHECK (опціонально): На рівні ініціалізації додано перевірку довжини тексту в полі details, щоб уникнути записів із порожнім описом.

Фрагмент коду ініціалізації схеми:
CREATE TABLE users (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL UNIQUE
);

CREATE TABLE requests (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    userId INTEGER NOT NULL,
    details TEXT NOT NULL,
    statusId INTEGER NOT NULL DEFAULT 1,
    accessTypeId INTEGER NOT NULL,
    createdAt DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (userId) REFERENCES users(id) ON DELETE CASCADE,
    FOREIGN KEY (statusId) REFERENCES statuses(id),
    FOREIGN KEY (accessTypeId) REFERENCES access_types(id)
);





Конкатенація — це просте додавання (склеювання) одного рядка до іншого. У нашому випадку ми беремо "заготовку" команди та просто приліплюємо до неї те, що ввів користувач.

// ПРИКЛАД НЕБЕЗПЕЧНОГО КОДУ
export const searchUnsafe = (query: string) => {
    // Вразливість: конкатенація рядків замість параметризації
    const sql = "SELECT * FROM requests WHERE details LIKE '%" + query + "%'";
    return db.all(sql); 
};

 Як працює атака (Механіка "зламу")Проблема в тому, що база даних не бачить різниці між вашим кодом (SELECT...) і даними користувача (query). Для неї це один суцільний наказ.Якщо користувач введе звичайне слово test, запит буде безпечним. Але якщо зловмисник введе Payload (штурмовий код): ' OR 1=1 --, відбувається наступне:Склеювання: База отримує рядок: SELECT * FROM requests WHERE details LIKE '%' OR 1=1 --%'.Підміна логіки: Завдяки одинарній лапці ('), зловмисник "вистрибує" з текстового поля і починає писати команди прямо в тілі SQL.Умова "Завжди ТАК": Вираз OR 1=1 каже базі: "Покажи записи, де в деталях є порожнеча АБО де одиниця дорівнює одиниці". Оскільки $1=1$ — це завжди правда, база ігнорує всі фільтри безпеки.Маскування: Символи -- перетворюють решту вашого оригінального коду на коментар, щоб база не видала помилку через "зайві" лапки в кінці.


Щоб запобігти цьому, я використовую параметризовані запити.
SELECT * FROM requests WHERE details LIKE ?При такому підході ми не "склеюємо" рядки. Ми передаємо базі окремо команду і окремо дані. Навіть якщо користувач введе ' OR 1=1 --, база сприйме це просто як один довгий і дивний шматок тексту, а не як частину команди.
